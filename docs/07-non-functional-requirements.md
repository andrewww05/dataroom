# Non-Functional Requirements

## Purpose

This document defines every non-functional requirement for Data Room, using the stable
`NFR-<CAT>-<nnn>` identifier space. It exists so that a QA engineer holding a mid-range Android
phone on a slow cellular connection can accept or reject a release without asking anyone what
"fast enough" or "accessible enough" means.

**Data Room is an internal tool.** The company builds it for its own staff. There is nothing to
buy, no plan to choose and no availability promise sold to anyone. That changes exactly two things
in this document: the scale targets are sized against a population we can count from the staff
directory rather than against an open market (see
[Population baseline](#population-baseline-the-known-internal-audience)), and every requirement
that existed to package or meter the product has been withdrawn. It changes nothing about the
security, privacy, accessibility and performance obligations below. Staff put **client** documents
into this tool and send links outward to external recipients, so those obligations bind harder
here than they would in a product a stranger could walk away from.

Four rules govern the whole file:

1. **Every NFR has a measurable target, a named measurement method, and a stated consequence of
   breach.** An NFR without all three is a defect in this document, not a soft requirement.
2. **Mobile is the primary measurement surface.** Where a target differs by form factor, the
   phone number is the binding one and the desktop number is the courtesy one. A requirement that
   passes on desktop and fails on the reference handset has failed.
3. **Evidence is labelled.** Figures taken from the research handed to this project carry their
   source. Anything reasoned here is marked `Assumption:` or `Estimate:` and must never be quoted
   onward as a sourced fact.
4. **This file cites numbers it does not own.** Under the single-source-of-truth rule,
   [06-business-rules-and-permissions.md](./06-business-rules-and-permissions.md) owns every
   threshold, limit, retention window, timing guarantee and permission rule;
   [05-functional-requirements.md](./05-functional-requirements.md) owns every requirement release
   tag and priority; [03-product-overview.md](./03-product-overview.md) owns the responsive
   size-class ladder; [10-success-metrics-and-analytics.md](./10-success-metrics-and-analytics.md)
   owns metric IDs and event names; and
   [09-domain-model-and-glossary.md](./09-domain-model-and-glossary.md) owns entity field names and
   error codes. Where a number appears here for readability it is written with the owning ID in
   parentheses, for example "60 seconds (BR-110)". A number in this file that contradicts its owner
   is a defect in this file.

## How an NFR is verified

Every NFR row below names one of these gates. The gate tells you who runs the check, when it
runs, and whether it can stop a merge or a release.

| Gate | Name | Runs | Blocking? | Owner |
| --- | --- | --- | --- | --- |
| **G1** | CI hard gate | Every pull request | Yes. Red CI blocks merge. | Engineering |
| **G2** | CI advisory trend | Every pull request, plus nightly on `main` | No. Posts a delta comment and opens a ticket when a threshold is crossed twice in a row. | Engineering |
| **G3** | Device QA checklist | Every release candidate, manually, on the physical reference handsets in [Reference environment](#reference-environment) | Yes. An unticked mandatory item blocks the release. | QA |
| **G4** | Automated device lab | Nightly on `main` and on every release candidate, real devices in a cloud device farm | Yes for release candidates, advisory nightly. | QA + Engineering |
| **G5** | Field data gate | Release-readiness review, using trailing 28-day p75 real-user monitoring segmented to mobile | Yes. A regression below target blocks the next feature release until remediated. | Engineering + Product |
| **G6** | Production monitor | Continuously | Not a merge gate. Breaching the alert threshold pages the on-call engineer and consumes error budget. | Engineering |
| **G7** | Periodic audit | On the stated cadence (quarterly, semi-annual or annual), internal or external as named | Yes at the audit checkpoint; findings become blocking backlog items. | Product + Engineering |
| **G8** | Design review gate | Before a story is marked Done, against the checklist in [Mobile UX specification](./08-mobile-ux-spec.md) | Yes. A story cannot be Done without it. | Design + Engineering |
| **G9** | Contract/schema gate | Every pull request that touches `packages/shared` or an API route | Yes. Contract drift fails the build. | Engineering |

Notation used in the tables:

- **Priority** uses MoSCoW: Must / Should / Could / Won't-for-now.
- **Release** is one of exactly four: **R1** (MVP), **R1.1** (Trust hardening), **R2**
  (Fast-follow), **R3** (Later). R1.1 is the named increment defined in
  [03-product-overview.md](./03-product-overview.md)'s release plan and carries the trust features
  staff will demand the first time a shared document leaks: dynamic per-viewer watermark,
  per-viewer access log, and share-link expiry. Where an NFR is the measurable form of a functional
  requirement, its release tag follows that requirement's tag in
  [05-functional-requirements.md](./05-functional-requirements.md), which owns the tag; this file
  never sets a release for a capability 05 already tags.
- **p75 / p95 / p99** are percentiles of the stated population; unqualified percentiles are over
  sessions, not over requests.
- "Reference handset" always means the device named in
  [Reference environment](#reference-environment), never a flagship.

### Test widths, mapped to the size-class ladder

**This file defines no breakpoints.** There is exactly one responsive size-class ladder and
[03-product-overview.md](./03-product-overview.md) owns it. The widths below are the *sample points*
CI and device QA measure at; each names the size class it exercises, and if the ladder changes in 03
this table follows without argument. Any number below that disagrees with 03 is a defect here.

The ladder, restated for readability only: **compact** below 600 CSS px, **medium** 600 to 839,
**expanded** 840 to 1279, **large** 1280 and above. Split view appears at **expanded and above and
only when height is at least 480 CSS px**; the persistent folder-tree rail and the docked details
inspector appear at **expanded and above**.

| Sample width | Size class | Used for |
| --- | --- | --- |
| 320 px | compact | WCAG 2.2 SC 1.4.10 reflow floor only. Nothing may require two-dimensional scrolling here. |
| 360 px | compact | Primary design and CI width. |
| 390–430 px | compact | Majority real-device width. |
| 599 px | compact | Upper edge of compact: assert nothing two-pane has appeared. |
| 600 px | medium | Lower edge of medium. Density and gutter changes only; still no split view, no tree rail, no docked inspector. |
| 839 px | medium | Upper edge of medium: assert the split view, tree rail and inspector are still absent. |
| 840 px | expanded | Lower edge of expanded. Split view (with the ≥ 480 px height check), tree rail and docked inspector appear here and nowhere earlier. |
| 1279 px | expanded | Upper edge of expanded. |
| 1280 px | large | Lower edge of large. Widest layout the product needs; nothing may *require* more. |
| 1920 px | large | Upper sanity check for max-width containment. |

Height is a first-class dimension, not an afterthought: a landscape phone can sit in **medium**
width while its height is under 480 CSS px, which is exactly the case a width-only rule breaks

### Population baseline (the known internal audience)

Every capacity figure in [NFR-SCALE](#nfr-scale--scale-and-capacity) is sized against this
population. It is worth saying plainly what changed when this became an internal tool: **the
population is now countable.** A product sold on an open market has to guess at its ceiling and then
defend the guess; this tool's staff population is an enumerable list in the identity provider and
the device inventory, and its external population is bounded by the invitations staff actually send.
So these numbers are not forecasts to be argued about — they are measurements to be re-read.

| Dimension | Baseline for R1 | Where the real number comes from | Review |
| --- | --- | --- | --- |
| Staff accounts | `Assumption:` the whole company, plus 25% headroom for growth and for contractor accounts | The identity provider's user list (see the identity assumption in [03-product-overview.md](./03-product-overview.md)) | Quarterly capacity review |
| Staff devices | `Assumption:` two per colleague — one managed laptop, one phone — with the phone often personal | The device-management inventory | Quarterly |
| Concurrent staff sessions at peak | `Estimate:` 25% of staff accounts, concentrated at 07:00–09:00 and 21:00–23:00 local | NFR-OBS-002 session data once the tool is live | Quarterly |
| External recipients per room | `Assumption:` tens, not thousands, for a normal room; NFR-SCALE-015 sets the enforced ceiling | The share-management screen's own counts | Quarterly |
| Anonymous link visitors on one room | Unbounded in principle and deliberately capped by NFR-SCALE-010 | Production monitoring | Monthly while any link is live |

Two consequences follow, and both are load-bearing:

1. **Staff-side targets are validated, not projected.** A capacity run that covers 100% of the
   directory plus 25% is a complete test, not a sample. Where a SCALE row below cites the staff
   population, the acceptance evidence is a run at that size, and the row is re-derived from the
   directory at each quarterly review rather than left as an aspiration.
2. **The recipient side is still open-ended, and is where the risk sits.** Staff control who
   receives a link but not what happens to it afterwards: a forwarded link, a room referenced in a
   wide email thread, or a document a client circulates internally all produce load nobody
   provisioned. Every recipient-facing limit is therefore enforced at the API with a stated ceiling
   and a graceful shed (NFR-AVAIL-013), never sized on the assumption that "it is only internal".

`Assumption:` no figure here implies exclusivity. An internal tool with a public share path has one
population it can count and one it cannot, and the uncountable one is the one facing the internet.

### A note on the mobile-first premise

The stakeholder constraint is that the majority of sessions arrive on a phone. That is a claim
about **when** this tool gets used — on site, in transit, from an email link at 07:00 — not a claim
about platform share anywhere. General platform mix is close to even and varies by region
(Statcounter for July 2026: worldwide mobile 52.57% / desktop 45.93%; United States desktop 54.0% /
mobile 43.85%; Europe desktop 51.79% / mobile 46.15% —
[worldwide](https://gs.statcounter.com/platform-market-share/desktop-mobile-tablet),
[US](https://gs.statcounter.com/platform-market-share/desktop-mobile-tablet/united-states-of-america),
[Europe](https://gs.statcounter.com/platform-market-share/desktop-mobile-tablet/europe)). Those
figures are kept here because they size the compatibility matrix (NFR-COMPAT-001, NFR-COMPAT-002),
not because they justify the premise.

The premise rests on behaviour instead, and on two facts about this tool's two populations:

- **The external recipient session is already phone-shaped and short.** A complete pitch-deck review
  averages 3.2 minutes, 23 seconds on page one and roughly 15 seconds per page thereafter
  ([Papermark's document metrics](https://www.papermark.com/pitch-deck-metrics)). A recipient
  opening a link from a mail app has no account, no install and no patience.
- **Staff are not at a desk when they need the document.** The nearest measured comparable
  profession spends a median 44% of working time on mobile
  ([NAR 2025 REALTORS Technology Survey](https://cms.nar.realtor/sites/default/files/2025-09/2025-realtors-technology-survey-report-09-18-2025.pdf)),
  and every comparable tool reviewed in
  [01-prior-art-and-ux-benchmark.md](./01-prior-art-and-ux-benchmark.md) ships a mobile surface that
  is a degraded subset of its desktop one. That is the failure mode this document exists to prevent.

`NFR-OBS-003` exists so that we replace both of those with our own measured figure. Unlike a market
number, ours is knowable: the population is the staff directory plus the recipients they invite, and
we instrument both from day one instead of arguing about them.

## NFR-SEC — Security

Security is enforced at the API, never in the UI. Hiding a button is not access control. Every
row here is testable against the API with a bare HTTP client and no browser.

| ID | Requirement | Target | Measurement method | Priority | Release | Consequence of breach |

| NFR-SEC-001 | Transport security | TLS 1.3 preferred, TLS 1.2 minimum; no plaintext HTTP except a 301 to HTTPS; HSTS with `max-age` ≥ 31536000 and `includeSubDomains`; TLS 1.0/1.1 and all RC4/3DES suites disabled | G1 CI check against a TLS scanner in the deploy pipeline; G7 quarterly external scan | Must | R1 | Deploy blocked. Any confidential deal document over plaintext is an immediate incident. |
| NFR-SEC-002 | Encryption at rest | All object storage and all database volumes encrypted with AES-256 or stronger, using provider-managed keys in R1, with the key-rotation procedure written down and rehearsed rather than assumed | G1 infrastructure-as-code assertion that no bucket or volume is created unencrypted; G7 annual review | Must | R1 | Deploy blocked. |

| NFR-SEC-011 | Share-link rate limiting and abuse containment | A single share token serving more than 200 distinct IPs in 1 hour raises an alert to the room Owner and every Manager on the scope and is throttled, not silently blocked (BR-228) | G6 monitor with a synthetic test; G1 unit tests on the limiter | Should | R2 | A leaked link is fanned out before the people responsible for it know. |
| NFR-SEC-012 | Revocation propagation time | Revoking a share, removing a member, or deleting a room takes effect for **all** subsequent requests within **5 seconds at p95 and 60 seconds absolutely (BR-108)**. | NFR-SEC-013 | Link controls | Public links support expiry (absolute timestamp, BR-087), password (verified server-side, rate-limited per NFR-SEC-009 and BR-089), download on/off (BR-090), and email capture (BR-092). | NFR-SEC-014 | Signed URL TTL and scope | Object URLs are signed for at most **60 seconds (BR-110)**, bound to the object key, the HTTP method, the requesting session or share token, and the grant's epoch counter. ## NFR-AVAIL — Availability and resilience

These are **internal service-level objectives**, not a promise sold to anyone. Nobody is owed a
credit when they are missed; the consequence is the error-budget policy in NFR-AVAIL-003, which
stops feature work. The targets are set by what the work needs — a colleague opening a room at
07:00 and an external recipient opening a link once, from a mail app, with no second attempt — and
not by a number chosen because it reads well next to somebody else's.

| ID | Requirement | Target | Measurement method | Priority | Release | Consequence of breach |
| --- | --- | --- | --- | --- | --- | --- |
| NFR-AVAIL-001 | Read-path availability (sign-in, list, search, preview, download) | **99.9%** monthly, measured as the fraction of successful synthetic probe minutes from three regions | G6 external synthetic monitoring, 60 s interval, reported monthly | Must | R1 | Error budget consumed (43.2 minutes/month). Exhausting it freezes feature deploys under AVAIL-003. |

## NFR-SCALE — Scale and capacity

Limits here are product limits, stated in-product, and enforced at the API. A limit the user
discovers by hitting a 500 is not a limit, it is a defect.

**These targets are sized for a known internal population, and the file says so on purpose.** The
staff side is bounded by the identity provider's user list plus headroom; the recipient side is
bounded only by what staff send outward. Both baselines, and the review cadence that keeps them
honest, are in [Population baseline](#population-baseline-the-known-internal-audience). Where a
figure below looks generous for one company's staff, that is deliberate in exactly two cases: a
limit that protects the *system* from one bad room (NFR-SCALE-010, NFR-SCALE-011) has to hold
against the internet, not against the directory; and a limit that would be expensive to raise later
(NFR-SCALE-002, NFR-SCALE-003, NFR-SCALE-016) is set once at a value nobody needs to revisit.
Numbers that 06 owns are cited with their BR.

## NFR-A11Y — Accessibility

Target standard: **WCAG 2.2 Level AA**, which became a W3C Recommendation on 5 October 2023
([W3C](https://www.w3.org/TR/WCAG22/)). The criteria below are called out individually because
they are the ones that bite on a touch screen, and because generic "WCAG AA compliant" is not a
testable statement.

**Nothing in this section is relaxed because the tool is internal, and two things are tightened.**
An internal tool is not optional: a colleague who cannot operate it cannot choose a different one,
so an accessibility defect here is a barrier to doing their job, and the company owns that as an
employment obligation rather than a product-quality metric. And the share-link path is opened by
external recipients about whom we know nothing at all — no device, no assistive technology, no
opportunity to give them a workaround. Both populations are reasons the bar goes up.

| --- | --- | --- | --- | --- | --- | --- |
| NFR-A11Y-001 | Overall conformance | WCAG 2.2 Level AA on every screen listed in [08-mobile-ux-spec.md](./08-mobile-ux-spec.md#core-screens), with a published accessibility conformance report and a named remediation owner for each open issue | G1 automated axe scan (zero critical, zero serious) on every screen in CI; G7 semi-annual manual audit by a trained tester including a screen-reader pass | Must | R1 | CI red for automated failures. ## NFR-COMPL — Compliance, audit and evidentiary integrity

**Honest position on certification.** Data Room will not hold SOC 2 Type II or ISO/IEC 27001
certification at R1, and this document does not pretend otherwise. An internal tool does not need a
certificate to be allowed to ship: the company is both the operator and the accountable party, and
an audit report addressed to itself proves nothing it does not already know. What R1 **must** do is
avoid designing certification out of reach, because two things reliably arrive later — a client
whose engagement terms require evidence of how their documents are handled, and an internal audit
that asks the same questions in different words. Both are answered from evidence that is either
being generated all along or cannot be reconstructed at all.

The requirements below therefore split into two kinds: controls that ship in R1 because
retrofitting them is prohibitive, and posture commitments that are explicitly deferred with a
stated precondition.

| ID | Requirement | Target | Measurement method | Priority | Release | Consequence of breach |
| --- | --- | --- | --- | --- | --- | --- |

## Performance budget enforcement

### The two-gate model

There are exactly two performance gates, and confusing them is the most common way a team ships
a slow product while showing green dashboards.

| | CI regression guard (G1) | Field acceptance gate (G5) |
| --- | --- | --- |
| What it measures | Lab metrics on the Lighthouse mobile preset, plus static bundle sizes | p75 of real user sessions, segmented to mobile, trailing 28 days |
| When | Every pull request | Release-readiness review |
| Authority | Blocks the merge | Blocks the next feature release |
| What it is for | Catching a regression in the change that caused it | Deciding whether the product is actually fast for actual users |
| What it is **not** | Not the acceptance criterion for any NFR-PERF row | Not a per-PR signal; it is too slow and too noisy for that |

Every performance story must state which of the two it is measured against. A story that says
"improves LCP" without naming the gate is not ready for sprint planning.

**Two rules protect this model, and neither is negotiable.**

1. **A Lighthouse score can never be an acceptance criterion.** Not for an NFR, not for a story, not
   for a release. It is a weighted composite of lab metrics under a synthetic throttle: it moves
   when the weighting changes, it can rise while a real interaction gets slower, and it can fall on
   a change that helps every user. The score appears in exactly one place in this document — an
   advisory row in the budget table — and the hard gates are the individual metric assertions
   beneath it. Any story, dashboard or definition of done that names a score as its target is
   rejected at review.
2. **Being an internal tool does not soften either gate.** A colleague who cannot avoid the tool has
   no way to express that it is slow except by not using it, and an external recipient expresses it
   by asking for an attachment instead. Both are silent failures, which is precisely why acceptance
   is a measured field number and not an opinion.

### What happens when a pull request regresses a budget

1. **CI fails.** The bot comments with the metric, the previous value, the new value, the budget,
   and the three largest contributing modules from the bundle diff.
2. **The author has three legitimate options**, in preference order:
   1. Fix it in the same pull request.
   2. Move the cost off the critical path (lazy-load the route, defer the dependency, move the
      work to the server, or replace the dependency).
   3. Request a **budget amendment**: a separate pull request that raises the budget, requires a
      code-owner approval from the performance owner, and must state what the user gets in
      exchange and which NFR-PERF row absorbs the cost. Amendments are reviewed monthly and
      reverted if the promised benefit did not materialise.
3. **What is not an option:** a bypass label, a skipped job, or a "we will fix it next sprint"
   comment. Estimate: on this team size the practical effect of a soft budget is no budget,
   because a budget that can be waived on the day it is inconvenient never binds.
4. **Repeat regressions.** Three budget amendments to the same budget in one quarter triggers a
   mandatory architectural review of that route before a fourth is considered.

### Field gate procedure (G5)

Run at every release-readiness review, on trailing 28-day data:

1. Pull p75 LCP, INP and CLS, **segmented to mobile**, for the five highest-traffic routes.
2. Pull the same segmented to the reference-device class (low device-memory bucket, `4g` or
   slower effective type) per NFR-OBS-002. This is the population the product is designed for
   and the aggregate figure hides it.
3. Pull the external-recipient path separately from the staff path. They are different populations
   on different devices with different tolerance, and the staff figure will flatter the recipient
   one: staff are on a partly-managed fleet, warm caches and a known network, and recipients are
   not.
4. Any "good" threshold missed at p75 on mobile blocks the next feature release for that route.
5. Record the numbers in the release record. A release with no recorded numbers is treated as a
   failed gate, because an unmeasured release cannot be compared to the next one.
